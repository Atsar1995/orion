## 1. Executive Summary

ORION Enterprise Platform v2.0 has completed its **foundational engineering phase**. Four independent business domains — **HCM**, **Finance**, **CRM**, and **Procurement** — have each achieved **Gate 5 Enterprise Certification** under the constitutional architecture ratified in P-014 and P-016. Every certified domain shares the same engineering pattern: a single composition root, PlatformStore-backed persistence, fail-closed RBAC (where REST surfaces exist), ADR-014 canonical event publishing, and a domain facade as the sole public boundary.

The platform has transitioned from **domain construction** to **enterprise integration**. Two cross-domain reference chains are engineering-complete and certified:

1. **HCM → Finance** — workforce cost and expense approval events post to the general ledger.
2. **CRM → Finance** — revenue recognition and sales order confirmation events post to the general ledger.

Procurement completes the procure-to-receive lifecycle within its domain boundary but has **no downstream consumers** for `procurement.goods.received` or invoice events. Inventory, Warehouse, and Hospitality remain outside Gate 5 certification.

**Gate 6** is the integration and operational readiness phase. Its purpose is to:

- Close cross-domain event chains (Procurement → Finance, Procurement → Inventory, Hospitality → Finance).
- Complete operational certification (restart resilience, live staging, performance baselines).
- Populate the ADR-014 EventContracts registry and achieve durable IIL production cutover.
- Advance all four Gate 5 domains from **CONDITIONAL GO** to production-ready posture.
- Authorize General Availability only when enterprise integration evidence exists.

### 2.3 Shared Constitutional Architecture

Every Gate 5 domain implements the same structural contract:

```
PlatformStore
  └── DomainStoreBacking (domain collections)
        └── EntityPersister (PostgreSQL Map-wrapper · ADR-007)
              └── create*Wiring() (composition root · ADR-015)
                    └── DomainFacade + CanonicalEventPublisher (ADR-014)
                          └── REST routes → get*ApiContextForRequest() (fail-closed RBAC)
```

**Constitutional laws (P-014.4 · ADR-015):**

- Domains **must not** import foreign repositories or SQL.
- Cross-domain writes **must** use ADR-014 canonical events via IIL (ADR-013).
- Business rules live in domain services and workflow modules — not in API routes.
- Organization isolation is enforced at repository and authorization layers.

## 10. Enterprise Communication Patterns

ORION enterprise communication follows a strict hierarchy. Cross-domain integration defaults to **asynchronous canonical events**. Synchronous cross-domain calls are discouraged and require ARB approval.

### 10.1 REST (Synchronous · Intra-Domain Primary)

| Rule | Description |
|------|-------------|
| **Scope** | UI and API operations within a single domain boundary |
| **Entry** | `/api/{domain}/*` route handlers |
| **Auth** | `get*ApiContextForRequest()` — fail-closed RBAC |
| **Services** | Pre-bound facade exports from `@/lib/{domain}` |
| **Prohibition** | REST routes must not import foreign repositories or execute cross-domain writes |

Each Gate 5 domain exposes REST through its composition root services. Cross-domain reads via REST are **sparse and approved only** — default is event-driven eventual consistency.

### 10.2 Canonical Events (Asynchronous · Cross-Domain Primary)

| Rule | Description |
|------|-------------|
| **Contract** | ADR-014 envelope · `eventVersion: "1"` · deterministic idempotency key |
| **Transport** | Durable IIL (ADR-013) · persist-before-ack · DLQ · replay |
| **Publish timing** | Post-commit only — after successful repository persistence |
| **Consumer** | Domain-specific inbound processor (e.g. `FinanceEventConsumer`) |
| **Registry** | EventContracts schema registry — Gate 6 population required |

**Reference chain pattern (mandatory for all new integrations):**

```
Domain Service → Repository commit → CanonicalEventPublisher.publish*()
  → IIL (persist-before-ack)
    → Consumer domain inbound processor
      → Consumer domain service → Repository commit → GL / stock / projection
```

### 10.3 PlatformStore (Persistence Authority)

| Rule | Description |
|------|-------------|
| **Authority** | PlatformStore is the sole persistence entry point (ADR-007) |
| **Backing** | Per-domain `{Domain}StoreBacking` collections on shared PlatformStore |
| **SQL isolation** | SQL executes only in `{Domain}EntityPersister` — never in services or routes |
| **Organization scope** | Every aggregate carries `organizationId` — enforced at repository layer |
| **Prohibition** | No shared mutable collections across domain boundaries |

### 10.4 Composition Root (Dependency Injection)

| Rule | Description |
|------|-------------|
| **Pattern** | `create{Domain}Wiring(platformStore)` — sole DI authority |
| **Wiring** | Repositories · authorization · canonical publisher · business services |
| **Facade** | `{Domain}Facade` — public entry; `readyForCertification` flag honesty |
| **Prohibition** | No singleton repositories in API routes · no `new InMemory*Repository()` in handlers |

### 10.5 Repository Isolation

| Rule | Description |
|------|-------------|
| **Interface** | Domain services depend on `{Domain}PersistenceRepository` interfaces |
| **Bounded contexts** | Repository aliases (e.g. `receiving`, `ordering`) share one adapter per wiring scope |
| **Cross-domain** | Foreign domain data accessed via events or approved facade reads — never via foreign repository import |
| **Prohibition** | `import { InMemory*Repository } from "@/lib/{other-domain}/persistence"` — ADR-015 violation |

### 10.6 RBAC (Fail-Closed Authorization)

| Rule | Description |
|------|-------------|
| **Catalog** | Per-domain permission codes · `domain:resource:action` format (ADR-009) |
| **API guards** | `get*ApiContextForRequest()` resolves route permission before handler execution |
| **Deny defaults** | Unauthenticated → 401 · unauthorized → 403 · unknown mutating route → deny |
| **Organization** | `resourceOrganizationId` must match `ServiceContext.organizationId` |
| **Platform** | Identity provides session · AuthorizationMiddleware enforces globally |

### 10.7 Health Monitoring

| Rule | Description |
|------|-------------|
| **Service** | `HealthStatusService` aggregates platform and domain health |
| **Domain checks** | `{domain}_platform` per Gate 5 domain |
| **Pipeline** | `{domain}EventPipelineRegistry.canonicalPublisherReady` |
| **Operations** | Gate 5 ops checklists define monitoring thresholds per domain |

### 10.8 Constitutional Prohibitions Summary

| Prohibition | ADR | Enforcement |
|-------------|-----|-------------|
| No direct repository sharing | ADR-015 | Import lint · code review · cert tests |
| No cross-domain SQL | ADR-007 · ADR-015 | EntityPersister isolation |
| No shared mutable state | ADR-015 | Separate store backings |
| No synchronous cross-domain mutation | ADR-014 | Architecture review |
| No Intelligence authoritative writes | P-014.1 §9 | Service boundary |
| No event publish before commit | ADR-014 | Service layer guards · workflow tests |

## 13. Enterprise Integration Principles

These principles are **constitutional**. They govern every Gate 6 integration mission and every future domain onboarding. Amendments require ARB ratification.

### 13.1 Foundational Principles

| # | Principle | Rule |
|---|-----------|------|
| **EIP-01** | **PlatformStore is authoritative** | All domain persistence resolves through PlatformStore. No alternate persistence paths. |
| **EIP-02** | **One composition root per domain** | `create{Domain}Wiring()` is the sole DI entry point. No hidden singletons. |
| **EIP-03** | **Facade-only public boundary** | Cross-domain imports use `@/lib/{domain}` facade exports only — never persistence internals. |
| **EIP-04** | **Canonical events only** | Cross-domain state propagation uses ADR-014 events via IIL. No direct aggregate mutation across domains. |
| **EIP-05** | **Post-commit publish** | Canonical events emit only after successful repository persistence. Rollback means no event. |
| **EIP-06** | **Finance hub for monetary truth** | All monetary convergence flows through Finance posting pipeline — not peer domain GL writes. |

### 13.2 Security & Isolation Principles

| # | Principle | Rule |
|---|-----------|------|
| **EIP-07** | **Organization isolation** | Every aggregate scoped to `organizationId`. Cross-tenant access is forbidden. |
| **EIP-08** | **Fail-closed authorization** | Missing permission → deny. Missing session → deny (when fail-closed enabled). Unknown route → deny. |
| **EIP-09** | **No repository sharing** | Domains must not import, instantiate, or inject foreign domain repositories. |
| **EIP-10** | **No cross-domain SQL** | SQL executes only in `{Domain}EntityPersister`. No cross-domain joins or foreign table access. |
| **EIP-11** | **No shared mutable state** | Each domain owns its `{Domain}StoreBacking` collections. No shared Map/SQL table across domains. |

### 13.3 Integration & Evolution Principles

| # | Principle | Rule |
|---|-----------|------|
| **EIP-12** | **No circular dependencies** | Domain dependency graph must remain acyclic. Event flows form directed acyclic graphs. |
| **EIP-13** | **Backward-compatible event evolution** | New event fields are additive. Breaking changes require Version 2 per ADR-020 dual-major window. |
| **EIP-14** | **Deterministic idempotency** | Every canonical event carries a deterministic idempotency key. Consumers must be idempotent. |
| **EIP-15** | **Intelligence is read-only** | Intelligence and Analytics consume projections. They never write authoritative domain state. |
| **EIP-16** | **Evidence-based integration** | Every new cross-domain chain requires certification tests before Gate 6 sign-off. |
| **EIP-17** | **Registry before production** | ADR-014 EventContracts registry entry required before production consumer deployment. |

### 13.4 Reference Chain Replication Law

Every new cross-domain integration **must** replicate the certified HCM → Finance or CRM → Finance pattern:

1. Define Version 1 canonical contract in domain outbound events catalogue.
2. Wire emission post-commit in domain service.
3. Implement consumer inbound processor in target domain.
4. Register EventContracts schema entry.
5. Add certification test proving end-to-end chain.
6. Document in domain integration guide.
7. Update this matrix (§7) and event catalogue (§9).

**Deviation requires ARB waiver with compensating controls documented in risk register.**
