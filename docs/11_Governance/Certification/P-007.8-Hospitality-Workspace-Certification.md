## Architecture Assessment

### Reference Pattern (mandatory for future workspaces)

```
types/hospitality-{domain}.ts
lib/hospitality/data/seed-{domain}.ts
lib/hospitality/{domain}/index.ts          → Domain Facade
lib/hospitality/{domain}/{domain}-events.ts  → IIL publisher
lib/hospitality/repositories/{Domain}Repository.ts
lib/hospitality/mappers/{domain}-brief.ts
app/api/hospitality/{domain}/*
tests/lib/hospitality/{Domain}Operations.test.ts
docs/03_Architecture/P-007.x-*.md
```

### Domain Facades (7 engines + 1 aggregator)

| Facade | Export |
|--------|--------|
| Inventory | `hospitalityInventoryService` |
| Reservations | `hospitalityReservationService` |
| Guests | `hospitalityGuestService` |
| Front Office | `hospitalityFrontOfficeService` |
| Housekeeping | `hospitalityHousekeepingService` |
| Billing | `hospitalityBillingService` |
| Analytics | `hospitalityAnalyticsService` |
| Workspace | `hospitalityService` |

### Repository Chain

`HospitalityRepository` → `InventoryRepository` → `ReservationRepository` → `GuestRepository` → `FrontOfficeRepository` → `HousekeepingRepository` → `BillingRepository`

Single implementation: `InMemoryInventoryRepository` / `defaultInventoryRepository`

### Domain Boundaries — Verified

- No duplicated Identity or Organization services
- No embedded authentication logic
- Billing decoupled from Finance (events published upward)
- Stay is operational entity; Reservation is commercial entity; Folio is financial entity
- Analytics aggregates — does not duplicate domain state
